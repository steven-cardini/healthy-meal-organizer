# Decisions

| ID   | Decision | Reason / rejected alternatives |
|------|----------|--------------------------------|
| D-1  | MVP = two alternating week blueprints only. Then swap, recipes, shopping list; finally health balance. | Small first release. |
| D-2  | One household, one shared password, everyone may edit. | No user accounts needed. Rejected: individual logins, several households. |
| D-3  | Plain PHP + Pico.css, server-rendered, plain HTML forms, no build step. No JavaScript framework in the MVP. | Fits shared hosting and keeps the code simple. No MVP feature needs JavaScript. Alpine.js (CSP build) can be added later if a feature needs it. Rejected: htmx; PHP JSON API + Vue SPA (two layers, more JS). |
| D-4  | Reusable meal list. A slot holds a meal, a note, or nothing. | The meal list is the pool for later swaps (with prep time) and recipes. Rejected: notes as special meals; free text per slot (would need a migration later). |
| D-5  | Weeks use the week blueprints alternately (FR-3). Each planned week stores its week blueprint; a week without one takes the other week blueprint than the week before. | No setting needed, and planning can switch the week blueprint (e.g. after holidays). Rejected: `cycle_start_date` in `config.php` (no value once weeks are planned); even/odd ISO week number (breaks in years with 53 weeks). |
| D-6  | Online-only PWA. The service worker caches only static files and an offline notice. | Never shows outdated data. Rejected: read-only offline view. |
| D-7  | Document root = `public/`. `config.php` lives in the repo root. A root `.htaccess` with `Require all denied` is a safety net; `public/.htaccess` allows access again. | Only public files are reachable, by design. The safety net protects config, data and docs if the document root is ever set wrong. Rejected: repo root as docroot with `.htaccess` deny rules. |
| D-8  | Day and week views have previous/next navigation. | Lets users look ahead, e.g. at next week on Sunday evening. Little effort. |
| D-9  | UI name "Menüplan"; week blueprints are called "Woche 1" / "Woche 2". The week view title shows the week blueprint and the dates, e.g. "Woche 1 · 14.–20.11."; the day view shows the week blueprint. | Common Swiss term. Rejected: the calendar week (KW), as weeks run Saturday to Friday (D-11). |
| D-10 | Login lasts 180 days after last use. Throttling: 5 failures per IP per 15 minutes. | Phones and tablets should rarely need a new login, and the login is reachable from the public internet. |
| D-11 | Time zone Europe/Zurich (fixed). Weeks run Saturday to Friday everywhere: week blueprints, week view, planning, swaps. The first weekday is one constant, `WEEK_START`. | Single Swiss household; the groceries arrive on Saturday. A constant, because changing it with existing planned weeks needs a data migration anyway. Rejected: Monday to Sunday with a separate Saturday-to-Friday planning week (one planning week spans two week views); a setting in `config.php`. |
| D-12 | Concurrent edits: the last save wins. | Small household; locking is not worth the complexity. |
| D-13 | No email in the MVP (no PHPMailer). | No feature needs it. |
| D-14 | Week blueprint editor: one form per slot with a choice *Gericht* / *Notiz* and one text field with suggestions. An empty field empties the slot. | Works without JavaScript; saving one slot keeps "last save wins" per slot. Rejected: a third choice "leer" (users could type a name and save it as empty by mistake); one form for all 28 slots (overwrites other people's edits). |
| D-15 | Renaming a meal to the name of another meal is rejected with an error. | Simple. Rejected: merging the two meals. |
| D-16 | Meal names are unique via a lowercase `name_key` column. | SQLite `NOCASE` only folds ASCII, so "Älplermagronen" and "älplermagronen" would both be accepted. |
| D-17 | Schema version in `PRAGMA user_version`. A database with another version than `SCHEMA_VERSION` is refused. | Later phases can migrate the production database instead of recreating it. An outdated schema is never used silently. |
| D-18 | Meal tags (FR-13) are one `NOT NULL` column per tag on `meal`, with a `CHECK` on the allowed values. The table stays `meal`. | The database enforces "exactly one value per tag". Rejected: a generic tag table (`type`, `value`), which cannot enforce this; renaming to `recipe` (in the glossary, a recipe is ingredients and steps). |
| D-19 | A meal can only be created with all tags. A new name in the week blueprint editor redirects to the new meal form; after saving, the slot is filled. | Mandatory tags. Rejected: creating meals without tags; an error message with a link (one more click). |
| D-20 | Prep time is a category (`quick`, `medium`, `slow`), not minutes. | Enough for planning and for finding quicker meals. Rejected: `prep_minutes`. |
| D-21 | One `leftovers` tag (`reheats_well`, `eat_fresh`). *Doppelte Menge kochen* / *Reste* are derived from the same meal in consecutive slots (FR-14). | "Cook more" depends on the plan, not on the meal. Rejected: separate values `double_batch` and `reheats_well` (almost always overlap); a leftover flag per slot. |
| D-22 | An error in the meal form shows the form again with the entered values (status 422), without a redirect. | The user would otherwise lose up to 7 choices. Rejected: Post/Redirect/Get with the values in the session. |
| D-23 | `meat` means all meat except poultry. `protein_source` has a value `none`, which is discouraged. | Common Swiss split "Fleisch / Geflügel / Fisch". Rejected: `beef_pork` (too narrow), `red_meat` (veal is not red meat). |
| D-24 | Tag values are lowercase snake_case codes with German UI labels. The meal form uses radio groups without a preselected value. | Consistent with `lunch` / `dinner`. All options are visible and need one tap; nothing is saved by accident. Rejected: drop-downs (options hidden), default values. |
| D-25 | The week view only shows hints you can act on (FR-14). The day view also shows protein source, prep time and kid suitability (FR-15); the meal list and the exchange options show the same tags (`SUMMARY_TAGS`). Digestibility, shelf life, leftovers and vegetables are shown in the meal form only. | The week view stays short. On the day view there is room for the facts that matter when cooking today. Rejected: all tags everywhere. |
| D-26 | Hints are chips below the meal name, each with an icon and a colour per kind. Every tag value has one icon (emoji), used in the meal form, the meal list and the day view; hints use the icon of the tag value they come from. Icons are set in CSS by a class per value (`tag_class()`), never without text. | One visual language that is learned once. Icons alone are not self-explanatory, so the text is always shown. Rejected: grey text after the name; icon-only badges. |
| D-27 | The week view is a list of day cards (lunch and dinner stacked), with three columns on wider screens. | The previous table was wider than a phone screen. Rejected: a table with horizontal scrolling. |
| D-28 | Navigation: a tab bar at the bottom on phones, at the top on wider screens. Swiping left / right on the day and week view drags the content with the finger and, past a quarter of the screen width or with a quick flick, follows the next / previous link. The old content then slides on from where the finger let go and the new content follows directly behind it (cross-document view transitions), without fading. Buttons and the tab bar change the page without animation. No swipe while zoomed in. Small JavaScript in `app.js`, no framework (D-3). | Native app feel and thumb reach. An animation only where a gesture asks for it. Everything still works without JavaScript or view transition support (buttons, no animation). Rejected: fading; sliding on button taps. |
| D-29 | CSS and JS URLs carry the file's modification time (`asset_url()`). | Browsers otherwise keep using an outdated `app.css` after a deployment. Rejected: manual version numbers (easy to forget). |
| D-30 | No logout. | Users never log out on their own devices; all devices can be logged out on the server (see `README.md`). |
| D-31 | Planned weeks, the planning of the next week and swaps (FR-16) are rows in one table `date_slot` keyed by (`date`, `meal_time`, `swap`), where `swap` is 0 for a planned week or planning and 1 for a swap. A row holds a meal, a note, or neither (empty, skipped). Both rows of an exchange or a move store the other slot (`partner_*`); the target of a move is flagged `moved`. Rows are kept after their date. | The week blueprints stay untouched; kept rows can feed the health balance later. The same code serves planning and swaps; a swap falls back to the planned week. Rejected: editing the week blueprints (changes every later week); one row per exchange (a slot can then be in two exchanges); two tables with the same columns (the SQL would need a variable table name). |
| D-32 | Swaps only from the day view, for slots that are not past (D-37), of the current week and of the next week once it is planned. Before that, the next week is changed by planning (FR-23). | Spontaneous changes once the groceries are ordered. A past meal was already eaten. |
| D-33 | Freshness (FR-20): ingredients arrive on the Saturday of the week and keep until the upper end of the `shelf_life` range. Warnings never block. The hint *Zutaten evtl. nicht mehr frisch* marks every meal planned too late, wherever it comes from. | Few false alarms; the household decides. A meal from a week blueprint can be too late as well. Rejected: lower end of the range (more warnings); marking user changes only. |
| D-34 | *Zurücksetzen* (of a swap or a planning change) also restores every slot linked to a restored slot by an exchange or a move, in either direction (FR-19), even if that slot was changed again later, except past slots (D-37). A slot keeps no swap history. | Otherwise a meal could be cooked twice or disappear. Predictable; the warning in the *⋯* menu names the other slots. A past slot keeps what was eaten. Rejected: following links in one direction only (after chained exchanges, a meal was cooked twice); keeping a later change of a linked slot (the moved meal disappears); hiding *Zurücksetzen* when an exchanged slot is past. |
| D-35 | Hints (FR-14) compare slots by date, including swaps. | Hints would be wrong after a swap. |
| D-36 | Swap and planning UI without JavaScript (D-3): small buttons below the slot, shown by a *⋯* button in its top right corner (`<details>`); *Zurücksetzen* saves at once, with a warning below it if it also restores other slots; each meal of the list is one submit button (one tap); filters are a GET form (prep time, protein source). | Fast on the phone, no extra confirmation for an action that can be undone. The menu keeps the day view calm. Alternative for later: small grey text links below the slot (one tap less). |
| D-37 | A meal time is past from 14:00 (lunch, `LUNCH_END`) or from the next day (dinner). Past meal times are shown in grey in the day and week view, with "vorbei" for screen readers only. The server decides when the page loads. | Shows at a glance what is already over; dinner stays relevant all evening. Rejected: an end time for dinner; a visible label; updating an open page with JavaScript. |
| D-38 | Move (FR-17): only from the target, a slot without a meal (*Gericht planen*). The moved meal is marked *verschoben*; the emptied slot shows *Verschoben auf Dienstag Mittag* (weekday and meal time, no date), or only *Verschoben* once the target holds something else. | Matches "the parents cook after all, so cook Thursday's meal on Tuesday". The weekday is enough within a week. The flag `moved` keeps *verschoben* when the emptied slot changes later. Rejected: also moving from the source (two ways for the same thing); a note on the emptied slot; *Nicht geplant* with a link to the week blueprint editor (it would not change this date). |
| D-39 | The next week is planned from its week blueprint and becomes a planned week with *Planung abschliessen*, which copies all its slots into `date_slot` and cannot be undone (with a confirmation). A week not planned by its Saturday becomes a planned week automatically. Changes to the week blueprints do not affect planned weeks, except the first week of use (it has no rows), which keeps following them. | The groceries are ordered for the planned week, so neither a change to the week blueprints nor *Zurücksetzen* of a swap may change it. A confirmation is simpler than reopening. Rejected: planning changes as plain swaps (*Zurücksetzen* would restore the week blueprint); reopening; planned weeks following the week blueprints. |
| D-40 | Choosing the other week blueprint while planning discards the planning changes of the week. | Exchanges and moves refer to the slots of the previous week blueprint. Rejected: keeping the changes. |
| D-41 | A week not planned yet shows the notice *Planung offen* at the top of the day and week view (FR-26), not in grey. | Grey means past (D-37), i.e. nothing to do; an unplanned week needs action. One notice per page is enough and readable without colour. Rejected: greying out its meals; a mark on every slot. |
| D-42 | Tabs: *Heute*, *Woche*, *Planen*, *Gerichte*. The week blueprint editor (*Wochenvorlagen bearbeiten*) has no tab; the *Planen* page links to it, and *Planen* stays selected there. | Planning is weekly, the week blueprints are edited rarely and only matters for planning. Four tabs fit on a phone. Rejected: a fifth tab. |
| D-43 | Planning changes are marked like swaps (*getauscht*, *verschoben*, …) until the week is planned; then only swaps are marked. | While planning, the marks show what differs from the week blueprint; afterwards, what differs from the planned week. Rejected: never marking planning changes. |
| D-44 | Phase 5 = ingredients without quantities, a recipe link per meal and a grocery list. No recipes stored in the app. | Enough to order the groceries; quantities can be added later. Rejected: recipes with steps, quantities and servings. |
| D-45 | Ingredients belong to their meal; only the category is shared per ingredient name. Tables `ingredient` (`name`, `name_key`, `category`) and `meal_ingredient`; an ingredient name no meal uses any more is deleted. The grocery list merges ingredients by `name_key` (D-16). | The category is chosen once and is the same on every list. Rejected: a category per meal ingredient (more typing; one name could show up in two categories); merging similar names (*Karotte* / *Karotten*), as the suggestions keep names consistent. |
| D-46 | Ten fixed ingredient categories (FR-28) with codes and German labels (D-24), in the order of the online shop. | Grouping by category matches how the groceries are ordered. Rejected: user-defined categories. |
| D-47 | Ingredient rows in the meal form: *+ Zutat* adds an empty row with small JavaScript in `app.js` (D-3). A known name selects its category; names already entered are not suggested again. Without JavaScript, one empty row is shown, and another after each save. | Separate fields per ingredient, without a page reload. Rejected: a text area with one ingredient per line; a submit button that reloads the form with more rows. |
| D-48 | The grocery list is computed from the entries of the week (FR-16, including swaps) on every request; nothing is stored. Only for planned weeks. | A change between planning and ordering must be on the list. Rejected: a copy taken at *Planung abschliessen*. |
| D-49 | Ticks on the grocery list are stored in `sessionStorage`, per week (key with its first date) and ingredient (`name_key`). Without JavaScript, the checkboxes work until the page is left. | Survives switching tabs and iOS reloading the app while ordering, but not closing it; another week starts without ticks. Rejected: in the database (shared across devices, not needed); plain checkboxes only (lost when leaving the page). |
| D-50 | The recipe link is shown in the day view only (in the *⋯* menu, D-54; edited in the meal form). Only `http` and `https` URLs are accepted. | Needed when cooking. Other schemes (e.g. `javascript:`) are unsafe. Rejected: in the meal list (each row is already a link to the meal form; for now), in the week view (D-25). |
| D-51 | Phase 6 rates the main meals of a week with the existing tags ([rules](requirements.md#health-balance-phase-6-draft)); no new tag before real data. A tag that only a few meals need (e.g. wholegrain, ultra-processed, fatty fish, deep-fried, sweet main meal, a second protein source as in *Chili con carne*) can be added later by a migration that sets existing meals to "no", so only those meals are edited. Changing a meal's tags also changes past dates. Deleting a meal empties it on past planned dates and removes past swaps to it, so the planned meal shows there again. | Breakfast and snacks are unknown, so shares (wholegrain, vegetables, dairy) cannot be measured; the meat rule also caps processed meat. The past is only a light look back. Rejected: `processed_meat` as a protein source; a `starch_source` tag (one more choice per meal for a share the app cannot measure); ultra-processed per ingredient (without quantities, one stock cube marks the meal); keeping deleted meals and old tags for past dates. |
| D-52 | Daily backup by a scheduled task running `bin/backup.php`: `SQLite3::backup()` into `data/backups/`, one copy per day, the last 14 kept. | A consistent copy even while the app writes, and it works with the host's older SQLite. Local copies are enough for now. Rejected: copying the file (inconsistent during a write); `VACUUM INTO` (needs SQLite 3.27); a URL called by the task (would be reachable from the web); off-site copies (for now). |
| D-53 | The database allows any week blueprint number from 1 (`CHECK (blueprint >= 1)`); the code uses Woche 1 and 2 only. | More week blueprints (roadmap, later) then need no migration: SQLite cannot change a `CHECK` without rebuilding the table. Rejected: an upper limit such as 4 (raising it needs the same rebuild). |
| D-54 | In the day view, the ingredients and the recipe link of a meal are in its *⋯* menu, above the swap actions. Slots that cannot be changed get the menu too, without actions. On a slot with leftovers (FR-14), only the hints for what is prepared fresh are kept: *Rohkost dazu* and *Alternative für Kinder*. | Everything needed for cooking in one place, while the day view stays calm. A cooked side dish is part of *Doppelte Menge*; raw vegetables and the children's alternative are not. Rejected: the recipe link below the tags; the ingredients always shown; no other hint with leftovers. |

## Open points (before or during implementation)

- **Migrations:** schema changes need migrations (D-17). With the first one: run each migration in a transaction, after a backup, tested on a copy of an old database (every push deploys to production).

Before production holds real data (the database can still be deleted until then):

- **Reset of production:** set `load_test_data` to `false`, then delete `db.sqlite`. The first logged-in request fixes the current week as *Woche 1*, which keeps following the week blueprints (FR-25), so reset right before entering the real week blueprints.
